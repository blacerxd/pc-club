# Технические требования: сайт ПК-клуба

## 1. Общее описание

Веб-приложение для сети ПК-клубов: бронирование мест, заказ еды, бонусная система, турниры, поиск клубов на карте. Архитектура — разделённое (decoupled) SPA-приложение: Django выступает исключительно как REST/WebSocket API-бэкенд, React — как единственный слой отображения (headless backend + frontend SPA).

Функциональный состав и модель данных подробно описаны в `pc-club-project-spec.md`. Этот документ описывает **технические** требования: стек, архитектуру, нефункциональные требования, процессы разработки и деплоя.

## 2. Архитектура

```
┌─────────────┐      HTTPS/JSON       ┌──────────────────┐      SQL       ┌────────────┐
│   Браузер    │ ───────────────────▶ │   Django + DRF    │ ─────────────▶ │ PostgreSQL │
│ (React SPA)  │ ◀─────────────────── │   (REST API)       │ ◀───────────── │            │
└─────────────┘      WebSocket        └──────────────────┘                └────────────┘
                                              │      ▲
                                              ▼      │
                                       ┌────────────────┐
                                       │  Redis          │◀── брокер Celery, backend Channels
                                       └────────────────┘
                                              │
                                              ▼
                                       ┌────────────────┐
                                       │  Celery worker  │── фоновые задачи (уведомления,
                                       │  + Celery beat  │   авто-отмена броней, waitlist,
                                       └────────────────┘   начисление бонусов)
```

Единая точка входа в проде — **nginx**: раздаёт собранный React как статику, проксирует `/api/` и `/ws/` на Django. Подробности проксирования и CORS описаны в переписке по связке фронт/бэк.

## 3. Технологический стек

### Backend
- Python 3.12+, Django 5.x, Django REST Framework
- PostgreSQL 15+ (расширение `btree_gist` для `ExclusionConstraint` на бронированиях)
- Redis — брокер Celery и channel layer для Channels
- Celery + Celery Beat — фоновые и периодические задачи
- Django Channels + Daphne — WebSocket (live-статус мест, лист ожидания)
- djangorestframework-simplejwt — аутентификация
- drf-spectacular — автогенерация OpenAPI-схемы
- Полный список зависимостей — в переписке про `requirements.txt`

### Frontend
- React 18+, Vite как сборщик
- react-router-dom — клиентский роутинг
- @tanstack/react-query — кэширование запросов к API
- Redux Toolkit или Zustand — глобальное состояние (auth, текущая бронь и т.п.)
- Tailwind CSS — стилизация
- react-big-calendar — календарь бронирования
- recharts — графики статистики в ЛК
- @pbe/react-yandex-maps — карта клубов
- react-hook-form + zod — формы и валидация

### Инфраструктура
- Docker + Docker Compose (dev и prod конфигурации раздельно)
- nginx — реверс-прокси и раздача статики фронта
- GitHub Actions — CI/CD
- Sentry — мониторинг ошибок (backend и frontend)

## 4. Требования к структуре репозитория

Монорепозиторий с раздельными точками входа `backend/` и `frontend/`, апп-модули Django вынесены в `backend/apps/`, фронт организован по фичам в `frontend/src/features/`. Полная структура и обоснование — см. переписку "в плане структуры директорий как сделать".

Обязательно:
- `.env.example` в обоих (`backend/`, `frontend/`) — шаблон переменных окружения без реальных значений
- `CODEOWNERS` — закрепление зон ответственности за участниками команды
- Файлы миграций Django (`**/migrations/*.py`) обязательно коммитятся в репозиторий — это часть кодовой базы, а не генерируемый артефакт

## 5. API — требования

- REST API, все эндпоинты под префиксом `/api/v1/` (версионирование с первого дня, чтобы не ломать фронт при будущих изменениях)
- Формат ответа — JSON, ошибки в едином формате (`{"detail": "...", "code": "..."}`)
- Пагинация обязательна для всех списочных эндпоинтов (`PageNumberPagination` или `CursorPagination` для лент)
- Фильтрация через `django-filter` (по клубу, зоне, статусу, дате)
- Обязательная OpenAPI-схема (`drf-spectacular`), доступная по `/api/schema/` и `/api/docs/` — нужна фронтенд-разработчикам и для демонстрации на защите
- CORS: явный whitelist origin'ов через `django-cors-headers`, `CORS_ALLOW_CREDENTIALS=True` если используются httpOnly-куки для refresh-токена

### Аутентификация
- JWT (access + refresh), access-токен живёт 15–30 минут, refresh — 7–14 дней
- Access-токен передаётся в `Authorization: Bearer`, хранится на фронте в памяти или `localStorage` (см. примечание по безопасности в п. 8)
- Разграничение прав через роли (`client` / `staff` / `admin`) и DRF `permission_classes`

### WebSocket
- Отдельные каналы (`/ws/zone/{zone_id}/`) для live-статуса мест и очереди ожидания
- Аутентификация WebSocket-соединения через токен в query-параметре или заголовке при handshake
- Фолбэк на обычный поллинг (раз в 10–15 сек), если WebSocket недоступен — не блокирующее требование для MVP

## 6. Требования к базе данных

- PostgreSQL как единственное хранилище реляционных данных
- Обязательные индексы: на поля фильтрации/сортировки (`Booking.start_time`, `Workstation.status`, `Club.city`)
- Ограничение целостности на пересечение бронирований на уровне БД (`ExclusionConstraint`), а не только проверкой в коде — критично для защиты от race condition при параллельных запросах
- Внешние ключи с явным `on_delete` (не оставлять дефолтный `CASCADE` бездумно — например, удаление пользователя не должно удалять историю его завершённых броней, лучше `SET_NULL` или soft-delete)
- Резервное копирование БД: ежедневный дамп (`pg_dump`) с ротацией, минимум для прод-окружения

## 7. Нефункциональные требования

### Производительность
- Время ответа API для типовых запросов (список клубов, список мест) — не более 300 мс на тестовом окружении
- Список мест/бронирований — обязательно с пагинацией, без выгрузки всей таблицы разом
- N+1 запросы к БД исключены через `select_related`/`prefetch_related` в вьюхах со связанными сущностями (например, бронирования со списком мест и клубов)

### Масштабируемость
- Приложение должно работать в нескольких воркерах (Gunicorn/Daphne с несколькими процессами) без потери состояния — состояние сессий/авторизации хранится в JWT и БД/Redis, не в памяти процесса

### Безопасность
- Пароли — только хешированные (стандартный Django `PBKDF2`/`Argon2`, не хранить в открытом виде)
- Секреты (пароли БД, `SECRET_KEY`, ключи API карт/SMS) — только через переменные окружения, не в репозитории
- HTTPS обязателен в проде (сертификат через Let's Encrypt/Certbot)
- Защита от CSRF для сессионных запросов, для JWT-эндпоинтов — стандартная защита DRF
- Rate limiting на чувствительные эндпоинты (логин, создание брони) — `django-ratelimit` или DRF throttling
- Валидация ввода на бэкенде обязательна даже при наличии валидации на фронте (фронтовая валидация — для UX, не для безопасности)

### Доступность и совместимость
- Адаптивная вёрстка (мобильные устройства — основной сценарий использования для брони "по пути в клуб")
- Поддержка последних двух версий Chrome/Firefox/Safari, мобильный Safari/Chrome

### Локализация
- Интерфейс на русском языке, формат даты/времени и валюты — российский (₽, ДД.ММ.ГГГГ)

## 8. Тестирование

| Уровень | Backend | Frontend |
|---|---|---|
| Unit | pytest-django, factory-boy для фикстур | vitest |
| Интеграционные | pytest-django + DRF `APIClient` на ключевые сценарии (создание пересекающейся брони должно быть отклонено) | @testing-library/react на ключевые формы/потоки |
| E2E (опционально) | — | Playwright/Cypress на сквозной сценарий: логин → бронь → заказ |

Обязательный тест-кейс: попытка создать две пересекающиеся брони на одно место параллельными запросами — должен быть отклонён на уровне БД, не только в коде вьюхи.

## 9. CI/CD

- GitHub Actions: линт + тесты на каждый push и pull request (отдельно для `backend/` и `frontend/`, с `working-directory`)
- Обязательный пройденный CI перед мержем в основную ветку (branch protection)
- Автодеплой на staging-окружение при мерже в `develop`/`main` (опционально для учебного проекта, но хорошо смотрится на защите)

## 10. Окружения

| Окружение | Назначение | Особенности |
|---|---|---|
| **Local (dev)** | Разработка каждого участника | `DEBUG=True`, локальный Postgres/Redis через Docker, hot-reload на фронте (Vite) |
| **Staging** | Тестирование перед демонстрацией/защитой | Копия прод-конфигурации, тестовые данные, не боевые ключи SMS/платежей |
| **Production** | Финальная демонстрация (если делаете реальный деплой) | `DEBUG=False`, HTTPS, реальные секреты только через переменные окружения сервера |

Конфигурация Django разделена на `settings/base.py`, `dev.py`, `prod.py` — исключает случайное попадание дев-настроек в прод.

## 11. Мониторинг и логирование

- Sentry (или аналог) — сбор необработанных ошибок на бэке и фронте
- Логирование действий администраторов (изменение брони, блокировка пользователя, начисление бонусов вручную) — отдельный аудит-лог (`BookingStatusLog` и аналогичные для других сущностей), нужен для админ-панели и разбора инцидентов
- Базовые метрики нагрузки на прод-сервере (CPU/RAM/диск) — минимум через `docker stats`/systemd, полноценный Grafana/Prometheus не обязателен для учебного масштаба

## 13. Ограничения и допущения MVP

Зафиксированные компромиссы (подробное обоснование каждого — в обсуждении MVP):
- Данные о железе и установленных играх вносятся вручную через админку, без автоматического агента на клубных ПК
- Оплата — без реальной интеграции с платёжным шлюзом на MVP-этапе (тестовый режим/только бонусами)
- Real-time обновления (WebSocket) — не блокирующее требование для MVP, допустим поллинг как временная замена
- Турнирная сетка — на MVP только регистрация участников, автоматическая генерация сетки и матчей — после MVP
